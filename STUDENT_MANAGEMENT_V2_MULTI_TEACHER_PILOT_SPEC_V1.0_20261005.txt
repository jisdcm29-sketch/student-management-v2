1. 최종 목표
============================================================
다른 교사에게 동일한 프로그램 URL을 제공하고,
각 교사가 자신의 개별 계정으로 로그인하여
자신의 반·학생·출석·성적·수업·조회/출력 데이터만 사용할 수 있게 한다.

교사는 다음 3가지 운영형태 중 하나를 사용할 수 있어야 한다.

A. APP_AUTO
- 서울대 학습앱 사용
- 앱 성적 자동 연동
- 필요 시 쓰기/기타 평가만 수동 입력
- 출석은 수동 또는 QR

B. MANUAL_ONLY
- 학습앱 미사용
- 서울대 단원평가를 교사가 직접 입력
- TOPIK 평가도 직접 입력
- 출석은 수동 또는 QR
- 조회/출력은 수동 입력 데이터 기반으로 정상 동작

C. HYBRID
- 일부 자동 앱 성적 사용
- 일부 교사 수동 성적 사용
- 자동/수동 성적은 서로 덮어쓰지 않고 출처를 구분하여 조회

핵심 원칙:
"같은 프로그램, 교사별 데이터 완전 분리, 자동/수동 모두 지원"

============================================================
2. 절대 보존 원칙
============================================================
1) 현재 유정태 SUPER_ADMIN 운영 데이터는 수정·혼합하지 않는다.
2) 기존 앱 자동 성적 연동 기능을 변경하지 않는다.
3) 기존 ScoreHub 90점 통과/과 개방/앱 진도 로직을 건드리지 않는다.
4) 신규 교사 데이터는 반드시 별도 Spreadsheet에 저장한다.
5) 프론트에서 spreadsheetId를 임의 지정할 수 없게 한다.
6) teacherId -> dataSpreadsheetId 매핑은 서버 Registry만 신뢰한다.
7) QR 출석도 교사별 데이터셋으로 라우팅한다.
8) TEACHER 계정에서는 Registry, 다른 교사 관리, 마이그레이션, 개발 기능을 숨긴다.
9) 자동 성적과 수동 성적을 같은 행/같은 계산값으로 합치지 않는다.
10) 실제 삭제보다 보관/상태변경을 우선한다.
11) 기존 운영본에 대한 회귀 테스트가 실패하면 배포하지 않는다.

3. 역할 및 권한
============================================================
3.1 SUPER_ADMIN

가능:
- 교사 계정 생성
- 교사 상태 ACTIVE/INACTIVE 관리
- 전용 Spreadsheet 생성/연결
- 임시 비밀번호 발급/초기화
- 온보딩 상태 확인
- 시스템 버전/배포 관리
- 필요 시 장애 점검

기본적으로 일반 교사용 화면에서는 숨길 기능:
- Registry 직접 관리
- 전 교사 목록
- 교사 데이터셋 관리
- 데이터 마이그레이션 도구
- 개발자/진단 메뉴
- 전체 시스템 설정

3.2 TEACHER

가능:
- 자신의 반 관리
- 자신의 학생 관리
- 자신의 출석 관리
- 수동 출석
- QR 출석
- 성적 관리
- 앱 자동 성적 조회(설정 시)
- 교사 직접 성적 입력
- 수업 내용 관리
- 과제/개별지도
- 조회/출력
- 학생·학부모용 출력
- 교사용 상세 출력

불가능:
- 다른 교사의 Spreadsheet 접근
- Registry 조회/수정
- 다른 교사 계정 관리
- 다른 교사 반/학생/성적 조회
- 시스템 마이그레이션
- 관리자용 완전삭제
- spreadsheetId 직접 지정

4. 계정/인증 시방
============================================================
4.1 로그인 방식

공통 URL 1개 사용.

교사가 입력:
- 교사 ID
- 비밀번호

로그인 성공 시 서버가 teacherId를 확정하고,
Registry의 dataSpreadsheetId를 서버에서 가져온다.

프론트는 dataSpreadsheetId를 알 필요가 없다.

4.2 신규 교사 ID

권장 형식:
T-TEACHER-001
T-TEACHER-002
T-TEACHER-003

현재 관리자:
T-ADMIN-001 유지

4.3 비밀번호

- 공용 비밀번호 금지
- 교사별 개별 비밀번호 사용
- passwordSalt / passwordVerifier 구조 유지
- 평문 비밀번호 저장 금지
- 임시 비밀번호 발급 후 첫 로그인 시 변경하도록 확장

Registry 추가 권장 필드:
mustChangePassword
onboardingStatus
lastLoginAt

기존 필드 뒤 오른쪽에만 추가한다.
기존 열 순서는 변경하지 않는다.

4.4 계정 상태

ACTIVE
- 로그인 허용

INACTIVE
- 로그인 차단
- 기존 세션도 다음 검증 시 폐기

필요 시 향후:
PENDING
SUSPENDED

단, 1차 파일럿에서는 ACTIVE / INACTIVE만 사용해도 충분하다.

5. 교사별 데이터 분리
============================================================
5.1 기본 구조

공통 프론트:
student-management-v2

공통 API:
student-management-v2-api

중앙 Registry:
학생관리시스템_V2_ADMIN_REGISTRY

교사별 데이터:
- 유정태 전용 Spreadsheet
- 테스트 교사 전용 Spreadsheet
- 실제 교사 A 전용 Spreadsheet
- 실제 교사 B 전용 Spreadsheet

5.2 서버 라우팅 원칙

모든 API 요청:
1) sessionToken 확인
2) requireSession_()
3) teacherId 확인
4) Registry에서 teacher 행 확인
5) teacher.dataSpreadsheetId 취득
6) 해당 Spreadsheet만 열기
7) 요청 처리

금지:
- 프론트 payload에서 spreadsheetId 받기
- URL 파라미터로 spreadsheetId 받기
- 다른 teacherId를 요청 payload로 받아 데이터셋 변경

5.3 ID 충돌

교사별 Spreadsheet가 완전히 분리되므로
S-001, C-001 등이 다른 교사에게 중복되어도 허용 가능.

단, 중앙 AuditLog/향후 중앙 통계에서는:
teacherId + studentId
teacherId + classId
조합으로 식별한다.

6. 신규 교사 Spreadsheet 생성 시방
============================================================
6.1 템플릿 기준

현재 정상 운영 중인 V2 교사 데이터 구조를 기준으로
"빈 교사용 템플릿"을 별도로 유지한다.

템플릿에 포함:
- 필요한 시트
- 헤더
- 기본 설정
- 수식/서식
- 숨김/보조 시트
- 필요한 데이터검증

포함 금지:
- 유정태 학생 데이터
- 유정태 출석 데이터
- 실제 성적
- 실제 학생 전화번호
- 실제 이메일
- 실제 QR 세션
- 실제 로그

6.2 생성 흐름

SUPER_ADMIN 신규 교사 등록:
1) 교사 정보 입력
2) teacherId 생성
3) 빈 템플릿 복제
4) 새 Spreadsheet 이름 지정
5) Registry에 dataSpreadsheetId 저장
6) role = TEACHER
7) status = ACTIVE 또는 파일럿 중 PENDING
8) 임시 비밀번호 설정
9) AuditLog 기록
10) 교사에게 URL + ID + 임시 비밀번호 전달

6.3 데이터셋 생성 실패

Registry에 teacher 행만 있고 Spreadsheet 생성이 실패한 경우
ACTIVE로 전환하지 않는다.

원칙:
"데이터셋 연결 확인 전 로그인 허용 금지"

7.1 AUTO

화면:
- 앱 자동 성적 강조
- 수동 입력은 보조
- 쓰기/별도평가 수동 입력 가능

자동 성적:
- 기존 ScoreHub 그대로 사용

수동 성적:
- 자동 점수 덮어쓰기 금지
- 별도 "교사 입력"으로 표시

7.2 MANUAL

화면:
- 앱 데이터 없음이 오류처럼 보이면 안 됨
- "학습앱 미사용" 표시
- 교사 직접 입력 평가를 주요 기능으로 표시

서울대 단원평가:
- 교재
- 과
- 읽기
- 듣기
- 쓰기
- 종합

TOPIK:
- 읽기
- 듣기
- 쓰기
- 필요 시 말하기/기타

자동 ScoreHub:
- 값이 없으면 단순 "앱 미사용/기록 없음"
- 통과/과 개방 판정 강요 금지

7.3 HYBRID

자동과 수동을 같이 표시한다.

표시 예:
앱 자동
교사 입력

자동 성적은 기존 진도 판정에 사용.
교사 입력 성적은 교사 평가 자료로 사용.
서로 덮어쓰지 않는다.

8. 성적 시방
============================================================
8.1 자동 성적

기존 기능 유지:
- LearningTestResults
- ScoreHubMastery
- WorkbookReadingResults
- WorkbookListeningResults
- TOPIK 관련 자동 결과

자동 서울대:
- 어휘
- 문법
- 종합
- 90점 통과
- 앱 진도
- 다음 과 개방

수정 금지.

8.2 수동 성적

Scores 시트의 TEACHER_MANUAL 사용.

서울대 기본:
- scoreType = SNU
- book
- lesson
- readingScore
- listeningScore
- writingScore
- mixedScore
- teacherNote
- sourceType = TEACHER_MANUAL

TOPIK:
- scoreType = TOPIK_I 또는 TOPIK_II
- readingScore
- listeningScore
- writingScore
- speakingScore(필요 시)
- teacherNote
- sourceType = TEACHER_MANUAL

8.3 조회 원칙

성적 관리:
- 자동 영역
- 교사 입력 영역
명확히 분리

조회/출력:
- 자동 성적
- 교사 입력 성적
같은 학생 종합 화면에서 함께 표시

학생·학부모 출력:
- 출처를 쉽게 이해할 수 있는 형태로 요약

교사용 상세 출력:
- 앱 자동/교사 입력 출처까지 표시

8.4 수동 입력 안전장치

저장 전 확인:
- 학생
- 평가일
- 평가유형
- 교재
- 과
- 점수

점수:
- 빈값 = 기록 없음
- 0 = 실제 0점
- 범위 초과 차단
- 숫자 아닌 값 차단

9. 출석 시방
============================================================
교사는 다음 두 방식 모두 사용 가능.

A. 수동 출석
- 반/날짜 선택
- 출석/지각/결석/조퇴 입력
- 현재 Attendance 사용

B. QR 출석
- 교사 자신의 반에서 QR 세션 생성
- 해당 teacher 데이터셋에만 저장

QR 필수 분리 키:
- teacherId
- classId
- sessionId

중요:
다른 교사의 QR 세션이 다른 교사 데이터셋에 기록되면 파일럿 실패로 판정.

동일 학생/날짜의 중복 출결은
기존 V2 우선 규칙을 유지한다.

- 신규 교사 생성
- 임시 비밀번호 초기화
- 계정 비활성화
- 데이터셋 연결 확인

1차 파일럿에서는
교사 삭제 기능은 만들지 않는다.

13. 보안/개인정보
============================================================
1) GitHub에 학생 개인정보 저장 금지
2) Spreadsheet ID 목록을 프론트에 하드코딩 금지
3) 비밀번호 평문 저장 금지
4) sessionToken 전체를 로그에 기록 금지
5) AuditLog에 개인정보 최소화
6) 교사별 데이터 교차 접근 차단
7) 완전삭제는 관리자만
8) 로그인 실패 반복 시 향후 rate limit 검토
9) 계정 비활성화 시 세션 무효화
10) QR 공개 URL로 교사 데이터가 노출되지 않도록 서버 검증

18. 파일럿 합격 기준
============================================================

필수:
1) 다른 교사 데이터 노출 0건
2) 다른 교사 데이터 수정 0건
3) 기존 자동 성적 회귀 0건
4) 수동 성적 정상 저장/조회
5) 수동/QR 출석 정상
6) 조회/출력 정상
7) TEACHER에서 관리자 기능 숨김
8) INACTIVE 로그인 차단
9) 로그아웃/세션 만료 정상
10) 신규 교사 데이터셋 생성 재현 가능

사용성 목표:
- 계정 전달 후 로그인까지 2분 이내
- 첫 반 생성까지 5분 이내
- 첫 학생 등록 및 출석 입력까지 10~15분 내 가능
- 별도 개발 지식 없이 사용 가능

3) 이전 frontend index/api-client 복구
4) 테스트 데이터셋 격리

2) 임시 비밀번호 전달 방식

권장: 불허

7) TEACHER의 반 완전삭제 허용 여부
권장: 불허 또는 폐강 처리만 허용

8) 관리자 화면에서 교사 생성 UI를 바로 만들지,
처음 1명은 수동 Registry 등록으로 검증할지
권장: 첫 파일럿은 수동 등록 -> 검증 후 UI 자동화

22. 첫 실제 개발 작업
============================================================
다음 작업은 "MT-1 TEACHER 권한 감사"로 시작한다.

목적:
현재 정상 프로그램을 수정하기 전에
실제 모든 API가 교사별 dataSpreadsheetId를 사용하고 있는지 먼저 확인한다.

점검 대상:
- Code.gs
- AuthService.gs
- RegistryService.gs
- DataRouter.gs
- Class 관련 API
- Student 관련 API
- Attendance 관련 API
- QR Attendance 관련 API
- ScoreHub 관련 API
- TeacherManualScoreV2.gs
- Lesson 관련 API
- Report 관련 API

점검 결과를 다음 3등급으로 구분:
SAFE
NEEDS_FIX
BLOCKER

BLOCKER가 하나라도 있으면 테스트 교사 계정 생성 전에 먼저 수정한다.
